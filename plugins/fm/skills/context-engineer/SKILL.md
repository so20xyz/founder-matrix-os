# fm:context-engineer - алдаа → eval → засвар → нотолгоо

Vault `<V>` = `${user_config.vault_path}` (эсвэл `~/.fmos/config.json`-ийн `vault`). Дүр: `<V>/03-Areas/AI Team/ai-workers/Context Engineer.md`. Скрипт: `S="${CLAUDE_PLUGIN_ROOT}/scripts"`, `python3 "$S"/fm_ce.py …` (Windows: `py -3`).

Локал store `<ce>` = `~/.fmos/context-engineer/` (`FMOS_CE_HOME`): `cards/<week>.jsonl`, `labels.jsonl`, `verdicts.jsonl`, `taxonomy.json`, `cases/<id>.json`, `results/`, `golden/<sid8>.md`, `names.txt` (people/-д байхгүй харилцагч, хүний нэр — мөр бүрт нэг, `#` тайлбар; ишлэлээс нуугдана). **Энэ store vault руу, repo руу хуулагдахгүй.** Vault руу зөвхөн `fm_ce.py publish-taxonomy` (нэр, тодорхойлолт, давтамж) → гишүүн бүрт тусдаа `03-Areas/AI Team/context-engineering/Алдааны ангилал — <гишүүн>.md` (`~/.fmos/config.json`-ийн `member`).

Горимыг `$ARGUMENTS`-аас сонго; хоосон бол `review`.

## review - trace review ба шошго

1. `python3 "$S"/fm_ce.py review --since YYYY-MM-DD` — `--since`-ийг **үргэлж** өг: `<ce>/cards/*.jsonl`-ийн хамгийн шинэ (долоо хоногийн) файлын огноо, анх удаа бол 7 хоногийн өмнөх огноо. Exit 2 (registry уншигдсангүй, vault алга) → **зогсоод** алдааг гишүүнд тайлагна. Тойрч гарах, гараар транскрипт уншихгүй.
2. `<ce>/cards/<week>.jsonl`-ийн картуудыг унш. Механик тоог (context, tool, тасралт) скрипт өгсөн — дахин бүү тоол.
3. **Open coding:** карт бүрт 1–3 богино тэмдэглэл «юу буруу/зөв болсон», тус бүр картын `quotes`/`first_prompt`-оос ишлэлтэй.
   **Шинэ зүйл гарахгүй болтол давт (loop-until-dry):** эхний давталтын дараа картуудыг өөр өнцгөөр (зорилго/brief, context хэмжээ, tool сонголт, гишүүний засвар/тасралт) дахин код. Давталт бүрт шинэ тэмдэглэлийг `<ce>/seen-<week>.json`-тэй (өмнө гарсан **ба** хасагдсан бүх тэмдэглэл) тулгаж, шинэ нь 0 бол `dry += 1`, шинэ гарвал `dry = 0`. `dry = 2` эсвэл 5 давталтад зогс. Хасагдсаныг ч `seen`-д үлдээ — эс бөгөөс дахин дахин санал болгогдож давталт дуусахгүй. Тайланд давталтын тоо ба карт хасагдсан бол тоог бич.
4. **Бүлэглэ** → `<ce>/taxonomy.json`-д шууд бич: `[{"id","name","definition","count","examples":[{"sid","quote"}]}]`, `count`-оор буурах эрэмбэтэй. Ангилал бүр бодит ишлэлтэй; ишлэлгүй ангилал үүсгэхгүй. Ишлэл ≤ 200 тэмдэгт, хүн/харилцагчийн нэр, файлын агуулга, token/key-гүй. **`name` ба `definition` нь ерөнхий** (жишээ «Зорилго тодорхойгүй эхэлсэн»): харилцагч, төсөл, хүний нэр, sid, ишлэл бүү оруул — эдгээр нь хуваалцсан vault руу гарна.
   **Эсэргүүцэх шалгалт (adversarial verification):** publish-ээс өмнө ангилал бүрийг **шинэ subagent (model: sonnet)** няцаахыг оролдоно: оролт = ангиллын `name`, `definition`, `examples` л. Гаралт = `confirmed|refuted|uncertain` + нэг мөр шалтгаан. Өнцөг тус бүрт өөр: (а) ишлэл тодорхойлолтыг үнэхээр харуулж байна уу, (б) өөр ангилалтай давхцаж байна уу, (в) нэр/тодорхойлолт ерөнхий юу (нэр, төсөлгүй). Анхдагч нь ангилал бүрт 1 шалгагч (а); `count ≥ 3` эсвэл засварын санал гаргах ангилалд 3 шалгагч (а, б, в), ≥ 2 `confirmed` бол үлдэнэ. `refuted` → хас эсвэл нэгтгэ; `uncertain` → үлдээж, тайланд «баталгаагүй» гэж тэмдэглэ. Ангиллыг бичсэн чи өөрөө шалгагч болохгүй.
5. `python3 "$S"/fm_ce.py publish-taxonomy` — бичсэн мөрүүдээ хэвлэнэ; нэр, төсөл үлдсэн эсвэл нүд хоосорсон бол `taxonomy.json`-ийг ерөнхий болгож засаад дахин ажиллуул.
6. **Алтан жишээ:** өмнөх шошгоос «good» авсан, эхний prompt нь зорилго + материал + «болсон» шалгууртай сешнийг `<ce>/golden/<sid8>.md` болго (эхний prompt-ын ишлэл + яагаад сайн, 3–5 мөр).
7. **Шошголох жагсаалт** (тусдаа алхам): 5–10 карт (ялгаатай/эргэлзээтэйг нь) → `<ce>/label-<week>.md` (локал store, vault руу **хэзээ ч** биш). Карт бүрт дүр (`role`), эхний prompt-ын ишлэл, гол тоонууд, нэг асуулт «сайн уу, муу уу, яагаад?». Гишүүнээс нэг нэгээр асууж, хариу бүрийг `python3 "$S"/fm_ce.py label <sid> good|bad <шалтгаан>`.

## eval - шүүгч ба regression

**Trace eval:**
1. Шүүх карт = шошготой эсвэл энэ долоо хоногийн шошголох жагсаалтад орсон карт; ангилал бүрт ажиллуулалт тутамд **≤ 10 карт**. Ангилал × карт бүрт **шинэ subagent (model: sonnet)**: оролт = нэг карт + нэг ангиллын `definition`, өөр context бүү өг. Гаралт = `pass|fail` + нэг мөр шалтгаан. Багцаар (нэг мессежд ≤ 10 subagent) илгээ, нэг том зэрэгцээ мессежээр биш.
   **Шүүгчийн самбар (judge panel):** шүүгчид `trusted: false` үед, эсвэл шүүгчийн шалтгаан эргэлзээтэй (картын ишлэлд тулгуурлаагүй) карт дээр ангилал × картад **3 шинэ subagent**, оролт ижил (нэг карт + нэг `definition`), бие биеийн хариуг харахгүй. Олонхийн (≥ 2) хариуг verdict болго; олонхи гараагүй бол (ж: нэг нь алдаа өгсөн, pass/fail тэнцсэн) verdict бүү бич, тайланд «маргаантай» гэж тоол. Самбартай үед ч ангилал тутамд ≤ 10 карт, нэг мессежд ≤ 10 subagent.
2. Хариу бүрийг (самбартай бол олонхийн нэгийг) `python3 "$S"/fm_ce.py verdict <sid> <category> pass|fail`.
3. Засвар санал болгосон сешн (чи) тэр засварын eval-ийг **өөрөө шүүхгүй** — шүүгч, самбарын гишүүн, эсэргүүцэх шалгагч болохгүй.
4. `python3 "$S"/fm_ce.py agreement` → `{"n","agree","trusted"}`. `trusted: false` (n < 30 эсвэл agree < 0.8) бол тайланд «шүүгчид хараахан итгэхгүй» гэж бич; засварыг зөвхөн механик тоо ба гишүүний шошгоор нотол. Самбар нь энэ босгыг **орлохгүй**: самбарын олонхи ч гишүүний шошготой тулгагдаж, ижил n ≥ 30, agree ≥ 0.8 дүрмээр итгэгдэнэ.

**Regression eval** (`<ce>/cases/<id>.json`, vault-ийн түр хуулбар дээр, гадагш бичдэг MCP унтраастай):
1. `python3 "$S"/ce_regress.py run --variant baseline --vault "<V>" --plugin-dir "${CLAUDE_PLUGIN_ROOT}" [--case ID]`
2. `python3 "$S"/ce_regress.py run --variant candidate --vault "<V>" --plugin-dir <tmp>/fm [--case ID]`
   `<tmp>/fm` = `${CLAUDE_PLUGIN_ROOT}`-ийн түр хавтас дахь хуулбар (vault дотор **биш**), санал болгосон ганц өөрчлөлттэй.
3. `python3 "$S"/ce_regress.py compare baseline candidate` → pass-rate, avg total_tokens.
`error` талбартай ажиллуулалт хэзээ ч pass биш; error-ийн шалтгааныг тайланд бич. Ажиллуулалт бүрийн token-ийг харуул. `--vault` өгөөгүй бол тохируулсан vault; олдохгүй бол exit 2.

**Кейсийн схем** — `<ce>/cases/<id>.json` (файлын нэр = `id`):
```json
{"id": "ask-before-build", "prompt": "…", "checks": [{"type": "asked_question"}, {"type": "max_baseline_tokens", "n": 120000}]}
```
Шалгалтын 7 төрөл ба түлхүүр:
- `file_exists {path}`, `file_absent {path}` — vault-ийн хуулбартай харьцангуй зам;
- `asked_question {}` — эцсийн хариунд ≥1 асуулт эсвэл `AskUserQuestion` дуудсан. Асуулт = «?»-ээр, эсвэл «уу/үү/юу/юү/вэ/бэ» сул үгээр төгссөн өгүүлбэр/мөр (код блок, URL доторх «?», «!»-ээр төгссөн мэндчилгээ тоологдохгүй; «бол» тоологдохгүй);
- `max_questions {n}` — эцсийн хариуны асуулт + `AskUserQuestion`-ий `questions`-ийн тоо ≤ n (бүхэл тоо; «анхдагчтай ганц асуулт» дүрэм → `n: 1`);
- `max_baseline_tokens {n}` — эхний context ≤ n (бүхэл тоо);
- `no_tool {name}` — тэр tool дуудагдаагүй;
- `text_contains {s}` — эцсийн хариунд `s` байгаа.
Буруу кейс (JSON алдаа, түлхүүр дутуу, үл мэдэгдэх төрөл) → тэр кейс `error: bad case …`-тай fail, бусад нь үргэлжилнэ; мөр бүр кейс дуусмагц `results/`-д нэмэгдэнэ.

**Кейс гаргах** — зөвхөн «good»/«bad» шошготой картаас: prompt-ыг ерөнхий болгож дахин бич (хүн, харилцагч, төслийн нэр, файлын агуулга, URL, token-гүй; картын ишлэлийг шууд бүү хуул). Шалгалтыг шошгын шалтгаанаас гарга («асуулгүй эхэлсэн» → `asked_question`, «context хэт том» → `max_baseline_tokens`). «bad» карт → засварын дараа pass болох ёстой кейс; «good» карт → pass хэвээр байх ёстой (regression хамгаалалт). 🔒 Finance/private сешнээс кейс хэзээ ч гаргахгүй.

## audit - статик context

`python3 "$S"/fm_ce.py audit` → зөвхөн нийт дүн: `baseline_ctx_median/max`, `peak_ctx_max`, `boot_bytes`, `inject_bytes`. Эх сурвалж тус бүрийг **хэмж**, бүү таамагла: `<V>/_system/BOOT.md` ба дүр бүрийн note-ийн байтын хэмжээ (`wc -c`), `inject_bytes − boot_bytes` (hook-ийн нэмсэн хэсэг), `baseline_ctx_median` − inject (skill/MCP жагсаалт, системийн prompt). Хамгийн том 3 эх сурвалжийг тоотой нь нэрлэж, тус бүрт нэг санал: юуг хасах/хойш ачаалах, аль ангиллыг засах.

## brief - хүсэлт → brief

`/ehle`-ийн 4 мөрт формат:
```
Зорилго: …
Хязгаар: …
Output: …
Done: …
```
`<ce>/golden/*.md`-аас хүсэлттэй хамгийн ойрыг нэгийг загвар болго. Дутуу мөр бол **нэг** асуулт, анхдагч утгатай.

## Засварын санал

Нэг санал = **нэг өөрчлөлт** (BOOT, agent, skill, hook, дүрийн note): засах ангилал, `ce_regress.py run` baseline/candidate, `compare`-ийн гаралт (хуулж), буцаах арга. Оноо унавал санал болгохгүй.
Засах арга олон байвал (≤ 3 хувилбар, тус бүр нэг өөрчлөлт, өөр өөр `<tmp>/fm-<n>`) бүгдийг ижил кейсүүд дээр `candidate-<n>` болгож ажиллуулаад `compare`-ийн механик тоогоор эрэмбэл (pass-rate эхэнд, дараа нь avg total_tokens); LLM-ээр оноо бүү өг. Хамгийн сайныг санал болго, бусдын тоог нэг мөрөөр хавсарга.
Засвар нь **зарчим** байна, кейс тутамд нэг дүрэм биш: «энэ кейс унасан» → «яагаад» (жишээ: brief-ийн шалгуур skill-д байхгүй) → тэр шалтгааныг засна. Батлагдсан засвар бүрийг `<ce>/changes.jsonl`-д нэмж бич (`{"date","category","change","before","after","revert"}`) — өмнөх/дараах тоо хуримтлагдана, мөр бүү устга. Гишүүн батлавал Architect-д task (`python3 "${CLAUDE_PLUGIN_ROOT}/skills/task/scripts/fm_task.py" new "<V>" "<гарчиг>" --owner architect`); repo-д өөрөө бүү бич.

## Долоо хоногийн гаралт (≤ 15 мөр)

1-р мөр: сешн N · «сайн» X% · хамгийн давтагдсан ангилал. Дараа нь: шүүгчийн agreement (trusted эсэх), нэг «яагаад» тайлбар (ямар context engineering зарчим), гишүүний prompt-ын оноо (зорилго/материал/шалгуур) ба чиг, нэг мөр «N карт шошголох → `<ce>/label-<week>.md`», засварын санал (байвал). Шошголох картуудыг тайланд бүү оруул. Оноо өсөөгүй бол урт тайлан бүү бич.
